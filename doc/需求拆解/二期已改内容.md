## 1. 后台手动拨付 H赠送释放订单

### 完成范围

- 新增 `H赠送释放` 后台菜单，菜单挂在 `质押管理` 下。
- 后台支持查询、新增、导出、冻结、解冻 H赠送释放桶。
- 后台新增时只输入钱包地址和赠送 H 总量，后端根据钱包地址查用户。
- 后台拨付来源固定为 `source_type=2`。
- `bucket_no`、`source_order_no` 使用后端生成的纯数字雪花 ID，不再加 `HGR` 字母前缀。
- 释放天数统一使用 `ConstantStatic.H_GIFT_RELEASE_DAYS = 100`，页面不允许修改释放天数。
- 状态收敛为 `1释放中、2已完成、3冻结`，不再保留未开始和作废状态。
- 保留冻结/解冻能力，删除/作废能力不再暴露。
- 不再使用 `next_release_date` 字段。
- 不再保留专用 `t_h_gift_release_log` 释放日志表，释放事实以 `xms_reward_record` 记录。

补充完成：

- 正常 ACP 入金继续走 `OpenController.stakeOrderCallback`。
- 有效 `t_stake_order` 创建成功后，自动创建 H赠送释放桶。
- 正常 ACP 入金释放桶 `source_type=1`，`source_order_no=stakeOrder.orderNo`。
- ACP/H 单价当前先从 `t_sys_para` 固定读取，后续再替换真实价格来源。
- `t_stake_order` 已记录 `deposit_source_type`、ACP/H 单价快照、本单折U价值、赠送比例快照、应赠送H总量。
- `t_stake_order.coin_type` 已删除，`stake_amount` 后续统一按 ACP 入金数量理解。
- H赠送释放桶创建时使用订单 `gift_h_amount`，不在释放桶服务里重新读取当前价格计算。
- 旧系统H换ACP入金继续走 `OpenController.oldHToAcpDepositCallback`。
- 旧系统回调 `amount` 表示旧系统已释放 H 数量，新系统按 H 价折 U 后再按 ACP 价换算成 ACP 入金数量。
- 旧系统H换ACP入金释放桶 `source_type=3`，`source_order_no=stakeOrder.orderNo`。
- 旧系统订单号/请求号写入 `t_stake_order.tx_hash` 做幂等。
- 正常 ACP 入金 `deposit_source_type=1`，旧系统H换ACP入金 `deposit_source_type=3`。
- 旧系统H换ACP入金仍走 `bizType=1` 后置结算链路，但不发社区/工作室补贴；仓位、业绩重算、等级重算和 `biz_status` 更新保留。
- 新增 `t_old_h_to_acp_deposit_record` 旧系统H换ACP入金审计记录表。
- `oldHToAcpDepositCallback` 成功创建 `t_stake_order` 后写入审计记录，记录旧系统订单号、旧 H 数量、H/ACP 单价快照、折U价值、ACP 入金数量和新系统订单。
- 新增后台菜单 `旧H换ACP入金记录`，挂在 `质押管理` 下，只提供查询和导出。

### 表和字段

新增表：

- `t_h_gift_release_bucket`：H赠送释放桶。
- `t_old_h_to_acp_deposit_record`：旧系统H换ACP入金审计记录。

核心字段：

- `bucket_no`：释放桶编号，唯一。
- `user_id`、`account`：新系统用户与钱包地址快照。
- `source_type`：来源类型，`1正常ACP入金、2后台手动拨、3旧系统入金`。
- `source_order_no`：来源订单号；本阶段后台拨付时等于后台生成的拨付单号。
- `total_amount`：赠送 H 总量。
- `released_amount`：已释放 H 数量。
- `remaining_amount`：剩余待释放 H 数量。
- `daily_release_amount`：每日释放 H 数量。
- `release_days`：固定 100。
- `released_days`：已释放天数。
- `start_date`：释放开始日期，`yyyyMMdd`。
- `last_release_date`：最后释放日期，`yyyyMMdd`。
- `status`：`1释放中、2已完成、3冻结`。

### 每日释放入账

已增加任务类型：

- `SysConstant.TSK_TYPE_106`
- `XmsTask.handelHGiftRelease106()`
- `AsyncTaskServiceImpl.handelHGiftRelease106()`

释放规则：

- 生产环境使用 `t_async_task(type=106,date=yyyyMMdd)` 控制每日幂等。
- 生产环境只释放 `status=1` 且 `start_date < releaseDay` 的释放桶，避免 00:00 到任务执行时间之间新建的桶当天释放。
- 非生产环境保留调试便利，不写任务标识，方便反复联调。
- 每日释放先收集释放桶，再批量构造 `RewardRecord`、`UserMoney.validNum9` 增量、释放桶进度更新，最后批量落库。
- 最后一天或剩余数量小于每日释放量时，释放全部剩余，避免小数尾差残留。
- 释放完成后状态改为 `2已完成`。
- 冻结状态 `3` 不释放。

钱包与流水：

- H 余额释放到 `t_user_money.valid_num9`。
- 钱包流水来源类型使用 `ConstantType.user_money_log_source_type.type_33`，含义为 `H赠送释放`。
- 不手写 `UserMoneyLog`，由 Canal 监听 `t_user_money` 变更后自动生成钱包流水。
- 奖励事实写入 `xms_reward_record`。
- 奖金流水来源类型使用 `ConstantType.xms_reward_record_source_type.type_11`，含义为 `H赠送释放`。

## 2. 提现从原来的只有 H 改为 H 和 ACP 代币

### 完成范围

- App 提现入参 `WithdrawalVo.ctp` 支持 `1、2、3、4、5、6、9`。
- `ctp=9` 表示 H 代币提现。
- `ctp=1、2、3、4、5、6` 按 ACP 体系提现。
- 提现配置改为按 `t_withdrawal_config.coin_type` 查询，不再只按单一 H 提现配置处理。
- 发起提现时按币种校验对应钱包余额。
- 提现扣款仍复用原钱包扣款逻辑，钱包流水来源类型继续使用提现相关现有类型。
- 自动免审核提现和后台审核通过提现都会把币种传给提现服务。
- 外部提现服务请求参数增加币种语义：`tokenName=H` 或 `tokenName=ACP`。
- 提现失败回调和后台审核驳回时，按原订单 `coinType` 退回对应钱包余额。

### App 入参与校验

入口：

- `xms/neptune-app/src/main/java/com/xms/app/controller/BizWithdrawalController.java`
- `xms/neptune-app/src/main/java/com/xms/app/entity/vo/WithdrawalVo.java`
- `xms/neptune-app/src/main/java/com/xms/app/service/impl/BizWithdrawalServiceImpl.java`

`WithdrawalVo.ctp` 允许值：

- `1`：节点收益，ACP 体系。
- `2`：静态，ACP 体系。
- `3`：动态，ACP 体系。
- `4`：财富仓，ACP 体系。
- `5`：保险仓/魔盒收益/手续费，ACP 体系。
- `6`：工作室收益，ACP 体系。
- `9`：H 代币。

余额校验：

- `ctp=1` 校验 `UserMoney.validNum1`。
- `ctp=2` 校验 `UserMoney.validNum2`。
- `ctp=3` 校验 `UserMoney.validNum3`。
- `ctp=4` 校验 `UserMoney.validNum4`。
- `ctp=5` 校验 `UserMoney.validNum5`。
- `ctp=6` 校验 `UserMoney.validNum6`。
- `ctp=9` 校验 `UserMoney.validNum9`。

### 提现请求币种

自动免审核提现：

- `BizWithdrawalServiceImpl.addWithdrawal(...)`
- `ctp=9` 时 `tokenName=H`。
- 非 `ctp=9` 时 `tokenName=ACP`。

后台审核通过提现：

- `xms/xms-dao/src/main/java/com/xms/dao/service/impl/WithdrawalServiceImpl.java`
- `coinType=9` 时 `tokenName=H`。
- 非 `coinType=9` 时 `tokenName=ACP`。

请求参数：

- `orderNo`：提现订单号。
- `address`：用户提现地址。
- `tokenName`：`H` 或 `ACP`。
- `amount`：提现数量扣除手续费后的实际打款数量。
- `sign`：按现有 `SignUtil.getSign(...)` 生成。

### 配置与记录

提现配置：

- `xms/xms-dao/src/main/java/com/xms/dao/domain/WithdrawalConfig.java`
- `xms/neptune-app/src/main/java/com/xms/app/entity/resp/WithdrawalConfigResp.java`
- 配置接口返回每个币种的提现开关、最小提现额、手续费比例、财富仓比例、保险仓比例。

提现记录：

- `t_withdrawal.coin_type` 继续记录用户本次提现币种。
- 提现回调按订单号查 `t_withdrawal`，成功改为提现成功，失败按原 `coin_type` 退回余额。

### 注意点

- 需要确认线上 `t_withdrawal_config` 已配置 H 和 ACP 相关可提现币种，否则对应 `ctp` 会提示配置不存在。
- 当前提现通道余额查询 `getWithdrawalCaBalance()` 仍固定查询 `tokenName=h`，如果后台需要展示 ACP 通道余额，需要再单独扩展。
- ACP 在本次提现请求里通过 `tokenName=ACP` 对接外部服务，需要确认外部提现程序已支持该值。
- 钱包币种字典、前端显示名称如果还按旧 H 口径展示，需要单独核对页面文案。

## 3. 旧用户体系迁移旧业绩字段接入

### 完成范围

- `t_user_info` 已增加旧系统业绩字段：
  - `old_performance`
  - `old_history_performance`
  - `old_sub_performance`
  - `old_umbrella_performance`
- `UserInfo` 已接入对应 Java 属性。
- `UserInfoMapper.xml` 已补充 old_* 字段映射和显式查询字段。
- `UserInfo` 已提供有效业绩读取方法：
  - `getEffectivePerformance()` = `performance + old_performance`
  - `getEffectiveHistoryPerformance()` = `history_performance + old_history_performance`
  - `getEffectiveSubPerformance()` = `sub_performance + old_sub_performance`
  - `getEffectiveUmbrellaPerformance()` = `umbrella_performance + old_umbrella_performance`

### 计算口径

- 新系统正常 ACP 入金仍只增加 `performance/history_performance/sub_performance/umbrella_performance`。
- 旧系统 H 换 ACP 入金仍只增加新系统真实业绩字段，不写 old_*。
- 迁移导入时才写 old_* 字段。
- 小区业绩按直推线 `effectiveUmbrellaPerformance + effectivePerformance` 重算。
- 层级等级按 `effectiveHistoryPerformance` 计算。
- 扫描到的 W3/挖矿等级业绩判断已改为使用有效业绩。
- 任务 101 本身主要使用已计算好的等级、层级、节点等级、仓位和贡献分，本次不改任务 101 奖励发放方法。
- 爆仓/保险链路主要按轮次、仓位、提现和钱包处理，未发现需要按 old_* 调整的业绩资格判断。
